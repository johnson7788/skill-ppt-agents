# 端到端测试方案（AI 编辑文档）

目标：能自动化验证"用户自然语言 → AI → 文档真的被正确修改"。重点是最容易出 bug 又最难测的一段：
**office 插件在编辑器里执行 `callCommand`/Builder API 的写回**。

## 0. 核心难点在哪

office 编辑的"真相"发生在**浏览器里的 ONLYOFFICE 编辑器 iframe**：
`插件 fetch 后端 → 拿 op → callCommand(Builder API) → 引擎渲染 → forcesave → callback → 落盘 uploads`。
这条链横跨 **backend + documentserver 容器 + 浏览器**三方，是唯一没把握、最该测的部分。
其余都在单进程内，好测：`/files/*`、`/chat/stream`（SSE）、白板（前端组件）。

## 1. 分层测试金字塔（下层便宜无浏览器，上层贵真链路）

| 层 | 测什么 | 依赖 | 工具 |
|----|--------|------|------|
| **L0 单元** | `parse_office_op`：op 校验、颜色/index 边界 | 无 | 已有自检 `python app/office_ops.py` |
| **L1 后端集成** | `/office/edit`（打桩 LLM）、`/files` round-trip、`/office/callback` 模拟落盘 | 起 ASGI app | `pytest` + `httpx.ASGITransport` |
| **L2 Builder 正确性** | 我们选的 Builder 脚本真能把背景改成指定色 | documentbuilder 镜像（**无浏览器**） | `docker run onlyoffice/documentbuilder` + unzip 断言 |
| **L3 全链路** | 插件面板→执行→保存→落盘 的**管道** | documentserver + backend + frontend + 浏览器 | Playwright |

原则：**能在下层证明的，就不要拿上层去证**。L2 把"op→文档正确性"和浏览器解耦——
若 L2 过而 L3 挂，问题一定在**管道**（选区读取、fetch、callCommand 派发、保存触发），不在 Builder 逻辑。

## 2. 各层怎么写

### L1 后端集成（先做，最快见效）

放 `backend/tests/test_office_edit.py`，风格同现有 test（可 `python tests/xxx.py` 或 `pytest`）。

**(a) `/office/edit` 打桩 LLM**：monkeypatch `litellm.acompletion` 返回一段 op JSON，断言接口回 `{op}` 且字段合法。
```python
import httpx
from httpx import ASGITransport
# monkeypatch litellm.acompletion -> 返回 choices[0].message.content = '{"type":"set_slide_background","slide":0,"color":"#FFFACD"}'
transport = ASGITransport(app=app)  # from server import app
async with httpx.AsyncClient(transport=transport, base_url="http://t") as c:
    r = await c.post("/office/edit", json={"text": "", "instruction": "第一页背景改浅黄", "doc_type": "slide"})
assert r.json()["op"] == {"type": "set_slide_background", "slide": 0, "color": "#FFFACD"}
```

**(b) `/office/callback` 模拟落盘**（复用 P2 验证手法）：monkeypatch `httpx.AsyncClient.get` 返回一段假 pptx bytes，
POST 一个 `status=2`、带合法 JWT token 的 callback body → 断言 `uploads/<user>/<path>` 被写成那段 bytes。
这验证"编辑器保存 → 后端落盘"这半条链，不需要真容器。

### L2 Builder 脚本正确性（关键，便宜，证明"改背景真的行"）

把 `code.js:applyOp` 里 `set_slide_background` 那段 `callCommand` 函数体，**等价搬进一个 docbuilder 脚本**
（同一套 `Api.*`，ONLYOFFICE Document Builder 与编辑器共用）：

```javascript
// bg.docbuilder
builder.OpenFile("/test/in.pptx");
var oSlide = Api.GetPresentation().GetSlideByIndex(0);
oSlide.SetBackground(Api.CreateSolidFill(Api.CreateRGBColor(0xFF, 0xFA, 0xCD)));
builder.SaveFile("pptx", "/test/out.pptx");
builder.CloseFile();
```
跑（无浏览器、无编辑器 UI）：
```bash
docker run --rm -v "$PWD/test:/test" onlyoffice/documentbuilder documentbuilder /test/bg.docbuilder
```
产物 `out.pptx` 用 §3 断言函数校验背景色 == `FFFACD`。
—— 这层一旦通过，就证明 `SetBackground` 这条 Builder API 选对了、颜色映射对了。L3 只需再验管道。

> 若某 op 的 Builder 写法在 docbuilder 里跑不通（如 `SearchAndReplace` 签名不对），先在 L2 修，最省。

### L3 全链路（Playwright，放 CI —— 本机无 chromium）

前置：`docker compose up -d documentserver`、后端:8585、前端:3585、`npm i -D @playwright/test`。

脚本要点（嵌套 iframe 用 `frameLocator` 链）：
```typescript
await page.goto("http://localhost:3585");
// 上传 + 打开一个 pptx（走文件树），等 OfficeEditor 的编辑器 iframe 就绪
const editor = page.frameLocator("iframe[name^='frameEditor'], #office-1 iframe");
// 编辑器里打开「AI 改写」插件 → 插件是编辑器再套一层 iframe
const plugin = editor.frameLocator("iframe.plugin, iframe[name*='plugin']");
await plugin.getByPlaceholder(/编辑指令|把第一页/).fill("把第一页背景改成浅黄色");
await plugin.getByRole("button", { name: "执行" }).click();
await page.keyboard.press("Control+S");          // 触发 forcesave→callback
// 轮询后端直到 uploads 里的 pptx mtime 变 / 背景色对
```
最后**读 `uploads/<user>/x.pptx`** 用 §3 断言。iframe 的 name/id 需按实际 DOM 调（`OfficeEditor` 的 holderId=`office-N`；
插件 iframe 由编辑器动态插入，POC 时用 devtools 抓准确 selector）。

## 3. 复用断言：pptx 背景色校验（L2/L3/手动通用）

```python
import zipfile, re

def slide_bg_color(pptx_path: str, idx: int = 1) -> str | None:
    """读第 idx 页（1 起）的 <p:bg> solidFill 颜色，返回 'FFFACD' 或 None。"""
    with zipfile.ZipFile(pptx_path) as z:
        xml = z.read(f"ppt/slides/slide{idx}.xml").decode("utf-8")
    m = re.search(r"<p:bg>.*?<a:srgbClr\s+val=\"([0-9A-Fa-f]{6})\"", xml, re.S)
    return m.group(1).upper() if m else None

# assert slide_bg_color("out.pptx", 1) == "FFFACD"
```
**这个函数当场验证过那个 bug**：对 python-pptx 改过的 `LongContextLLM.pptx` 跑 → 返回 `FFFACD`，
证明**色确实写进了磁盘的 `<p:bg>`**，"看不到"纯属编辑器没重载（P6.0 已修），不是写失败。
（注意：它只证 `p:bg` 写没写对，**不能**判断是否被铺满整页的封面图/形状盖住——那要另查 slide 里的 `p:pic`/全屏 `p:sp`。）

## 4. 手动冒烟清单（写自动化前先跑通链路）

- [ ] `docker compose up -d documentserver` 后 `GET :8081/healthcheck` → `true`
- [ ] 工作台打开 pptx，编辑器工具栏出现「AI 改写」插件按钮
- [ ] 选中一段文字 → 插件 → "改正式点" → 选区被替换（验 `PasteText`）
- [ ] 不选 → "把第一页背景改成浅黄色" → 背景变黄（验 `callCommand`+`SetBackground`+`Asc.scope`）
- [ ] Ctrl+S → 后端日志 `ONLYOFFICE 保存回写` → `uploads` 文件 mtime 变、`slide_bg_color()==FFFACD`
- [ ] 插件 iframe fetch `:8585/office/edit` 跨域放行（CORS 已 `*`）

## 5. 其它模块 E2E（较简单）

- **聊天 SSE**：`httpx` POST `/chat/stream` 消费流，断言事件序列含 `tool_step`/`narrator_card`/`done`（LLM 打桩或真 key 冒烟）。
- **白板**：Playwright 开 `.excalidraw` → 选中节点 → 指令 → 断言 scene 变化；落盘断言 `GET /files/raw`。也可前端 `vitest` mock `excalidrawAPI`。
- **文件底座**：`/files/tree|raw`(GET/PUT)、`/files`(DELETE) 的 CRUD round-trip（L1 一并覆盖）。

## 6. 落地顺序（先便宜后昂贵）

L0（已有）→ **L1 后端集成**（纯后端，最快）→ **L2 docbuilder**（证 Builder，无浏览器）→ **手动 L3 冒烟**（§4）→ CI 里补 **Playwright L3**。
本机无 chromium，L3 自动化放 GitHub Actions（`ubuntu` + `playwright install chromium` + `docker compose` 起 documentserver）。
